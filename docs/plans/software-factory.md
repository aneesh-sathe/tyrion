# Tyrion as a software factory manager

Status: proposed. Not yet broken into tracker issues.

## Objective

You describe work in a sentence. Tyrion decides how to break it apart, how many
agents that is worth, which harness each piece should go to, runs them in
parallel under containment, integrates and verifies the result, and reports
back through the harness you were already using.

One conversation. No JSON. No supervising Worker windows.

## What is already true

This is a smaller change than it sounds, because most of the machinery exists
and is proven with real models:

- One Entry Session is the only surface you talk to, projected into Claude Code
  or Codex through MCP. Natural language already becomes a proposal, because
  the Entry tool instructs the host model to construct it and never ask you for
  JSON.
- Work is already expressed as Assignments with dependencies, write scopes,
  criteria and per-Assignment resources.
- Cross-harness concurrency is proven: Codex and Claude ran at the same time on
  disjoint Assignments and produced one verified integrated artifact, 20.1
  seconds faster than serial.
- Containment, routing, integration, verification, interruption and restart
  recovery all work against real models.

So the factory floor exists. What is missing is a manager standing on it.

## What is missing

### 1. Nothing decomposes a specification

`proposed_plan` is written to the database and **never read by any code**.
Every plan revision in the system is sourced `control_plane`, meaning
deterministic decomposition. There is no path where a model reads a goal and
proposes the breakdown.

Today the Principal supplies the plan Assignment by Assignment, or gets a
single legacy Assignment. This is the central gap.

### 2. The Entry Session is capped at one Worker

`src/entry_mcp.rs` rejects `max_attempts != 1` and
`max_worker_concurrency != 1`. Two lines. The cap was correct for a walking
skeleton and is now the thing preventing a factory.

### 3. Concurrency is not capacity aware

The per-Worker profile is 2 vCPU and 6144 MiB, inherited from the OpenShell
MicroVM and never revisited. The Docker VM on the development machine has 12
CPUs and 8.2 GB, so **one** Worker's memory ceiling is 75% of the whole VM.

Nothing reads host capacity. Nothing sizes a plan to fit it.

### 4. Progress does not scale

`tyrion_status` returns a full projection. That reads well for one Worker and
becomes unusable at twenty. There is no digest of what is running, blocked,
done, or waiting on you.

### 5. OpenCode is not supported

Claude Code, Codex and Pi have adapters. OpenCode does not.

### 6. Setup is expert-only

The runtime configuration is generated by a script the author wrote for the
author. There is no install path, and the README is a reference dump rather
than an explanation.

## Design decisions

**The planner rents its model from a harness.** Tyrion dispatches a Planning
Assignment to a Worker whose job is to return a proposed plan. It does not
embed a provider API client. This keeps the existing rule that all model
intelligence arrives through complete Agent Harness Worker Configurations, adds
no second credential path, and means the planner is contained exactly like
every other Worker. The manager is model-backed; it does not own a brain.

**A proposed plan is a proposal, never an authority grant.** The planner
proposes Assignments *within* an Authority Envelope the Principal accepts. It
cannot widen repositories, paths, actions, destinations or effects. The
deterministic Control Plane validates every proposed plan before committing it:
each criterion owned exactly once, write scopes disjoint or ordered by
dependency, authority inside the envelope, resources inside capacity.

**Agent count is an outcome, not a goal.** The spec already says raw Worker
count is not success, and that stands. Tyrion sizes a plan to the useful
parallelism in the work and the capacity of the machine. If a job is
genuinely three independent pieces, spawning thirty agents is waste, not scale.

**Spend stays observed, not enforced.** Consistent with the 2026-09-25 change:
no harness gives Tyrion a hard monetary ceiling, so it reports cost rather than
gating on it. At factory scale this matters more, not less, so cost must be
*visible* per Commission and per Assignment.

**Local only.** One per-user daemon, Workers on this machine. Remote execution
would change the security model completely and is out of scope.

## Slices

| # | Slice | Depends on | Independently verifiable outcome |
| --- | --- | --- | --- |
| 1 | Capacity-aware concurrency | none | Tyrion reads host CPU and memory, derives a safe Worker ceiling, and sizes per-Worker resources per configuration rather than one global profile. A plan that cannot fit is held with an explicit reason, not attempted. |
| 2 | Lift the single-Worker cap | 1 | An Entry Session can accept a multi-Assignment plan and run Workers concurrently up to the derived ceiling. |
| 3 | The Planner | 2 | A goal in one sentence produces a validated multi-Assignment plan, proposed by a contained planning Worker and committed only after deterministic validation. `proposed_plan` is consumed. |
| 4 | Factory status | 2 | One compact projection answers what is running, what is blocked, what is done, and what needs the Principal, at twenty Workers as readably as at one. |
| 5 | `brew install` and `tyrion init` | 1 | A clean machine with Docker reaches a working first Commission through two commands. |
| 6 | README | 5 | A reader learns what Tyrion is, what it does, how to install it, and how to use it, without reading the spec. |
| 7 | OpenCode adapter | 2 | OpenCode joins Claude Code, Codex and Pi as a Worker harness. |

Slices 5 and 6 are independent of the planner and deliver usability first.
Slice 3 is the heart and the largest.

## Risks worth stating now

**Plan quality is unproven.** A model proposing a decomposition may produce
overlapping scopes, wrong dependencies, or criteria nothing can verify.
Deterministic validation catches structural faults; it cannot catch a plan that
is merely bad. The first real test is whether a planned Commission beats the
same work done serially.

**Integration conflicts scale with parallel writers.** Two disjoint Assignments
integrate cleanly. Twenty writers touching adjacent code will produce
reconciliation Assignments, and that path has only been exercised in fixtures.

**Cost scales with agent count and is not bounded by Tyrion.** Codex used
40,411 input tokens for hello world. Twenty agents on a real task is real
money, and the provider cap is the only ceiling.

**The planner is a new failure mode.** If planning fails, nothing runs. It
needs the same recovery treatment as any other Assignment.

## Explicitly out of scope

No remote or cloud Workers. No direct provider API integration. No agent-count
target as a product claim. No new scheduler, queue or broker. No web UI. No
support for harnesses beyond the four named.
